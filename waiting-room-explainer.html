How the waiting room works

Shoppers join a line for an event. A separate controller decides how fast the line moves, based on how healthy the backend is. Each person who reaches the front gets a signed token that unlocks seat selection and checkout.

Joining and the draw

  • Login required, one entry per account. Joining twice returns your existing entry (200, not 201). Joining a sold-out event returns 409.
  • Before the on-sale time you have no position. Status is pre_sale, and arrival order does not matter.
  • At T0 the pool is shuffled once (Fisher-Yates) and positions are assigned in that order. Anyone joining after the draw goes to the back.

The valve

Each controller tick sets the rate to zero if any gate below trips, checked in that order. Otherwise:

rate = clamp(200 − active, 0, 50) per second, or the operator override in its place. An override never bypasses a gate.

"Active" means admitted, token still live, and no confirmed order since admission.

Admission

Every second admit() turns the commanded rate into whole people, carrying the fraction. Saved-up budget is capped at one second's worth, so an idle spell cannot become a burst. Each admitted person moves the head pointer and gets a signed token.

Fails closed: a rate command older than 30 s counts as rate 0, so a dead controller stops admissions instead of leaving the tap open.

The token

v1.kid.claims.HMAC-SHA256, with account, event and expiry in the claims. The availability, holds and orders routes verify it: 401 if invalid or expired, 403 if issued for a different event or account, 429 beyond 10 requests/s per token.

Once it expires your state is expired. Rejoining creates a new entry at the back of the line.

What a shopper sees

Polling GET /queue/me returns one of six states: pre_sale, waiting, paused, admitted, expired, sold_out. While waiting, the response includes ahead and pollAfterSeconds, about half the expected wait clamped to 5–60 s (60 s when there is no position or the rate is 0).
